## Positioning

**Rust 后端与前端边界** 位于 Tauri 知识树的 **架构与运行模型** 分支，紧接在「系统 WebView 与轻量打包」之后。你已经知道 Tauri 是"Web UI + 系统 WebView + Rust 后端"的三层架构，现在要深入理解：Rust 层和前端层之间到底画了一条什么线？哪些事情该谁做？这条线为什么这样画？

## Analogy

把 Tauri 应用想象成一家**银行**。

前端（WebView 里的 UI）是**营业大厅**：客户（用户）在这里看到界面、填写表单、提交请求。大厅环境舒适、漂亮、交互友好，但它本身不能金库操作、不能转账、不能修改账户数据。

Rust 后端是**银行内部系统**：金库、账务系统、风控系统、合规审查。它处理所有敏感操作和核心业务逻辑，但不会直接面对客户。

**边界**就是柜台窗口：客户通过柜台提交请求（invoke 命令），柜员（Tauri 框架）验证身份和权限（capabilities/permissions），然后把请求传递到内部系统处理，最后把结果返回给客户。

这条边界的核心目的：**隔离关注点 + 安全控制**。

- 前端专注于用户体验和界面交互
- Rust 专注于系统能力、数据安全和性能敏感逻辑
- 边界确保前端不能越权访问系统资源

## Core Mechanism

### 一、前端能做什么（WebView 中的 JavaScript/TypeScript）

前端运行在系统 WebView 里，本质上和浏览器环境类似：

| 能力 | 说明 |
|------|------|
| DOM 操作 | 渲染 UI、响应用户交互 |
| CSS 样式 | 布局、动画、主题 |
| JavaScript 计算 | 纯前端逻辑（表单验证、数据格式化等） |
| Web API | `fetch`（网络请求）、`localStorage`、`setTimeout` 等 |
| 框架能力 | React/Vue/Svelte 等框架的全部前端能力 |

**前端不能直接做的事情：**
- ❌ 读写本地文件系统
- ❌ 执行系统命令（shell）
- ❌ 访问操作系统 API
- ❌ 创建系统托盘、原生菜单
- ❌ 直接访问环境变量、进程信息
- ❌ 多线程计算（受限于 WebView 的 Worker 模型）

### 二、Rust 后端能做什么

Rust 后端是 Tauri 应用的"原生层"，拥有完整的系统访问能力：

| 能力 | 说明 |
|------|------|
| 文件系统 | 读写文件、遍历目录、监听文件变化 |
| 系统命令 | 执行 shell 命令、启动子进程 |
| 窗口管理 | 创建/关闭/调整窗口、全屏、最小化 |
| 系统托盘 | 创建托盘图标、托盘菜单 |
| 原生菜单 | 创建应用菜单、快捷键绑定 |
| 网络请求 | 原生 HTTP 客户端（不受 CORS 限制） |
| 数据库 | SQLite 等本地数据库操作 |
| 加密/解密 | 原生加密库 |
| 多线程 | Rust 的线程模型，CPU 密集型计算 |
| 插件系统 | 扩展更多系统能力 |

### 三、边界的三条核心原则

**原则 1：前端展示，Rust 执行**

```
用户点击按钮 → 前端处理点击事件 → 前端通过 invoke 发请求
→ Rust 接收请求 → Rust 执行系统操作 → Rust 返回结果
→ 前端接收结果 → 前端更新 UI
```

前端永远是"请求者"，Rust 永远是"执行者"。

**原则 2：前端不信任，Rust 把关**

Rust 后端是安全边界。前端发来的每个请求，Rust 都应该：
- 验证参数合法性
- 检查权限配置（capabilities/permissions）
- 决定允许还是拒绝

前端代码可以被用户修改（DevTools），所以永远不能信任前端传来的数据。

**原则 3：关注点分离**

| 放在前端 | 放在 Rust |
|---------|----------|
| UI 渲染和动画 | 文件 I/O |
| 表单验证（用户体验层） | 数据持久化 |
| 路由和页面切换 | 系统 API 调用 |
| 状态管理（UI 状态） | 业务核心逻辑（敏感部分） |
| Web API 调用 | 需要高性能的计算 |
| 用户交互处理 | 安全相关操作（加密、鉴权） |

### 四、边界的实际体现：项目结构

```
my-tauri-app/
├── src/                    # 前端代码（TypeScript/JavaScript）
│   ├── main.ts            # 前端入口
│   ├── App.tsx            # React 组件（或其他框架）
│   └── styles.css         # 样式
├── src-tauri/             # Rust 后端代码
│   ├── src/
│   │   ├── lib.rs         # Tauri 命令注册、应用构建
│   │   ├── main.rs        # 应用入口
│   │   └── commands/      # 命令模块（按功能分组）
│   ├── Cargo.toml         # Rust 依赖
│   └── tauri.conf.json    # Tauri 配置
└── package.json           # 前端依赖
```

前端和 Rust 是两个完全独立的构建系统：
- 前端用 npm/pnpm/yarn 管理依赖，用 Vite/Webpack 等构建
- Rust 用 Cargo 管理依赖，用 rustc 编译
- Tauri 负责把两者打包到一起

### 五、边界上的"灰色地带"

有些操作放在哪边都可以，需要根据场景判断：

**场景 1：数据校验**
- 前端做：用户体验好（即时反馈），但不安全
- Rust 做：安全，但有 IPC 往返延迟
- 最佳实践：**两边都做**。前端做即时 UX 校验，Rust 做安全校验

**场景 2：大量数据处理**
- 前端做：受限于 WebView 的 JS 引擎性能
- Rust 做：性能更好，可以利用多线程
- 最佳实践：**计算密集放 Rust**，前端只负责展示结果

**场景 3：配置存储**
- 前端做：`localStorage` 简单但不安全
- Rust 做：可以加密存储、写入文件系统
- 最佳实践：**敏感配置放 Rust**（如 API key），普通 UI 偏好放前端

## Code Example

```rust
// src-tauri/src/lib.rs
// Rust 后端：定义命令，作为前端的"服务接口"

use tauri::State;
use std::sync::Mutex;

// 应用状态（共享数据）
struct AppState {
    db_path: String,
}

// 命令 1：读取文件内容
// 前端不能直接读文件，必须通过这个命令
#[tauri::command]
fn read_config_file(path: String) -> Result<String, String> {
    // Rust 执行文件读取
    std::fs::read_to_string(&path)
        .map_err(|e| format!("Failed to read file: {}", e))
}

// 命令 2：执行计算密集型任务
// 大量数据处理放在 Rust 层，性能更好
#[tauri::command]
fn process_data(items: Vec<f64>) -> f64 {
    // 模拟复杂计算
    items.iter().sum::<f64>() / items.len() as f64
}

// 命令 3：使用共享状态
#[tauri::command]
fn get_db_path(state: State<AppState>) -> String {
    state.db_path.clone()
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .manage(AppState {
            db_path: "/data/app.db".to_string(),
        })
        .invoke_handler(tauri::generate_handler![
            read_config_file,
            process_data,
            get_db_path,
        ])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

```typescript
// src/main.ts
// 前端：通过 invoke 请求 Rust 后端执行操作

import { invoke } from "@tauri-apps/api/core";

// ✅ 正确：通过命令请求读取文件
async function loadConfig() {
  try {
    const content = await invoke<string>("read_config_file", {
      path: "/etc/myapp/config.json"
    });
    const config = JSON.parse(content);
    renderConfig(config);
  } catch (error) {
    showError(`Failed to load config: ${error}`);
  }
}

// ✅ 正确：计算密集型任务交给 Rust
async function analyzeData(numbers: number[]) {
  const average = await invoke<number>("process_data", {
    items: numbers
  });
  displayResult(average);
}

// ❌ 错误：前端尝试直接访问文件系统（不会工作）
// const content = await fetch("file:///etc/myapp/config.json");

// ✅ 前端负责 UI 逻辑
function renderConfig(config: Record<string, string>) {
  const el = document.querySelector("#config");
  if (el) {
    el.textContent = JSON.stringify(config, null, 2);
  }
}

function showError(msg: string) {
  console.error(msg);
}

function displayResult(avg: number) {
  const el = document.querySelector("#result");
  if (el) {
    el.textContent = `Average: ${avg}`;
  }
}
```

这段代码展示了边界的实际运作：
- **Rust 定义"服务接口"**：`#[tauri::command]` 函数就是后端暴露给前端的 API
- **前端调用"远程服务"**：`invoke()` 就像调用 REST API，只不过"服务器"是本机 Rust
- **类型安全**：参数和返回值都有类型，Tauri 自动序列化/反序列化
- **错误处理**：Rust 返回 `Result<T, E>`，前端用 try/catch 捕获

## Common Misconceptions

**误解 1：Rust 后端就是写 UI 逻辑的地方。**
纠正：Rust 后端不处理 UI 渲染。UI 始终由前端 Web 技术在 WebView 中渲染。Rust 的角色是"系统服务提供者"，处理文件、网络、系统 API 等原生能力。

**误解 2：前端和 Rust 可以直接共享内存或变量。**
纠正：前端和 Rust 运行在完全不同的环境中。它们之间的通信必须通过 IPC（invoke/event），数据需要序列化（通常用 JSON 或 bincode）。没有"共享指针"或"共享引用"这回事。

**误解 3：所有业务逻辑都应该放在 Rust 中。**
纠正：不是所有逻辑都需要放 Rust。纯 UI 逻辑（表单验证、路由、动画状态）放在前端更合适。Rust 适合处理：系统操作、安全敏感逻辑、性能敏感计算、需要多线程的任务。关键是判断"这个操作需要系统权限或高性能吗？"

**误解 4：前端框架的选择会影响 Rust 后端。**
纠正：前端用 React、Vue、Svelte 还是纯 HTML，对 Rust 后端来说没有区别。Rust 只关心 `invoke` 调用的命令名和参数类型，不关心前端用什么框架渲染 UI。这就是边界的好处——两层可以独立开发和替换。

**误解 5：Rust 后端代码改动后需要重新编译整个应用。**
纠正：开发模式下，Tauri 支持 Rust 代码热重载（通过 `cargo watch` 或 Tauri 的 dev server）。修改 Rust 代码后会自动重新编译 Rust 部分，前端部分不受影响（前端有 Vite/Webpack 的热更新）。

## Socratic Check

**检验问题 1：**
假设你要做一个 Tauri 文件管理器应用，用户点击"删除文件"按钮。这个操作应该完全由前端处理，还是需要通过 Rust 后端？为什么？

答案：必须通过 Rust 后端。删除文件是系统级操作，前端在 WebView 中没有文件系统访问权限。流程应该是：前端捕获点击 → invoke("delete_file", { path }) → Rust 验证路径合法性 → Rust 检查权限配置 → Rust 执行删除 → 返回结果给前端 → 前端更新文件列表。

**检验问题 2：**
如果你有一个 10 万条数据的排序任务，应该放在前端 JavaScript 还是 Rust 后端？

答案：放在 Rust 后端更合适。原因：(1) Rust 的排序性能远优于 JavaScript；(2) Rust 可以利用多线程并行排序；(3) 不会阻塞 WebView 的主线程（前端 UI 保持流畅）。前端只负责发送数据和展示排序结果。

## Quick Summary

- 前端（WebView）负责 UI 渲染和用户交互；Rust 后端负责系统能力、安全把关和性能敏感逻辑
- 边界通过 `invoke`（命令）和事件系统连接，数据通过序列化传递，不能共享内存
- 三条原则：前端展示/Rust 执行、前端不信任/Rust 把关、关注点分离
- 灰色地带的判断标准：需要系统权限或高性能 → Rust；纯 UI 逻辑 → 前端
- 前端框架的选择对 Rust 后端透明，两层可以独立开发
