## Positioning

这是 Tauri 知识树的根基概念。理解了它，你就掌握了 Tauri 的"为什么"——为什么它比 Electron 轻、为什么它安全模型不同、为什么跨平台需要额外关注。后续所有概念（Rust 后端、IPC、Runtime）都是建立在这个架构选择之上的。

## Analogy

回顾并升级之前的类比：

上次我们把 Tauri 比作一家"自带厨师但借用厨房灶台"的餐厅。现在把这个类比再推进一步。

想象你要开一家连锁餐厅（跨平台应用）：

- **Electron 方案**：每家店都自带一整套厨房设备（Chromium + Node.js），统一、可控，但成本高、占地方。
- **Tauri 方案**：利用每个城市已有的公共厨房设施（系统 WebView），你只带自己的厨师（Rust 后端）和菜谱（前端代码）。开店成本低，但需要适应不同城市厨房的差异。

关键推论：
- Windows 的"公共厨房"是 WebView2（基于 Edge/Chromium）
- macOS 的"公共厨房"是 WKWebView（基于 WebKit）
- Linux 的"公共厨房"是 WebKitGTK

你的"厨师"（Rust 后端）是统一的，但"厨房设备"（WebView）因城市而异。

## Core Mechanism

### 三层架构回顾

```
┌─────────────────────────────────────────┐
│           前端 UI 层                      │
│   HTML / CSS / JavaScript (React/Vue等)  │
│   运行在系统 WebView 中                   │
├─────────────────────────────────────────┤
│           系统 WebView 层                 │
│   Windows: WebView2 (Edge/Chromium)      │
│   macOS:   WKWebView (WebKit)            │
│   Linux:   WebKitGTK                     │
│   Android: Android WebView               │
├─────────────────────────────────────────┤
│           Rust 后端层                     │
│   窗口管理 / 命令注册 / 插件系统           │
│   安全边界 / 权限控制 / 系统调用           │
└─────────────────────────────────────────┘
```

### 轻量打包的本质

Tauri 的"轻"不是功能少，而是架构选择的结果：

| 对比维度 | Electron | Tauri |
|---------|----------|-------|
| 浏览器运行时 | 随应用捆绑 Chromium | 复用系统 WebView |
| Node.js | 随应用捆绑 | 不捆绑，用 Rust 替代 |
| 典型包体 | 60-150 MB+ | 2-10 MB |
| 内存占用 | 较高（完整 Chromium） | 较低（系统 WebView） |
| 跨平台一致性 | 高（自带运行时） | 中（依赖平台 WebView） |

### 轻量打包带来的 trade-off

**优势：**
- 包体小：不需要捆绑 Chromium (~100MB+) 和 Node.js
- 启动快：系统 WebView 通常已预加载
- 内存省：共享系统 WebView 进程
- 安全好：Rust 的内存安全 + 明确的权限边界

**代价：**
- WebView 版本差异：不同平台的 WebView 引擎和版本不同，需要测试
- 前端环境受限：没有 Node.js API，不能直接用 `fs`、`child_process` 等
- 依赖管理：Windows 上需要确保 WebView2 Runtime 可用

### 关键认知锚点

1. **Tauri 不是"用 Rust 写界面"**——界面仍然是 Web 技术，Rust 是后端
2. **系统 WebView ≠ 用户安装的 Chrome**——是操作系统组件，Windows 11 预装 WebView2
3. **轻量 ≠ 功能弱**——通过 Rust 命令和插件，Tauri 可以访问大量系统能力
4. **前端 ≠ Node 环境**——需要系统能力时，必须通过 Tauri API 或 Rust 命令

## Code Example

```rust
// src-tauri/src/lib.rs
// Rust 后端：注册命令，提供系统能力入口

#[tauri::command]
fn greet(name: &str) -> String {
    format!("Hello, {}! This comes from Rust backend.", name)
}

#[tauri::command]
fn get_system_info() -> String {
    // Rust 可以直接访问系统信息
    // 前端做不到这一点，必须通过命令请求
    let os = std::env::consts::OS;
    let arch = std::env::consts::ARCH;
    format!("Running on {} ({})", os, arch)
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .invoke_handler(tauri::generate_handler![greet, get_system_info])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

```typescript
// src/main.ts
// 前端 UI：运行在系统 WebView 中
// 不能直接访问文件系统、系统信息等
// 必须通过 invoke 向 Rust 后端发请求

import { invoke } from "@tauri-apps/api/core";

// 调用 Rust 命令
const greeting = await invoke<string>("greet", { name: "Tauri" });
console.log(greeting); // "Hello, Tauri! This comes from Rust backend."

const sysInfo = await invoke<string>("get_system_info");
console.log(sysInfo); // "Running on windows (x86_64)"
```

这段代码展示了 Tauri 的核心分工：
- **前端**：负责 UI 渲染和用户交互，运行在 WebView 中
- **Rust 后端**：负责系统能力，通过 `#[tauri::command]` 暴露给前端
- **IPC 桥梁**：`invoke()` 是前端向 Rust 发请求的通道

## Common Misconceptions

**误解 1：Tauri 应用需要用户安装 Chrome。**
纠正：Tauri 使用的是系统 WebView 组件（如 Windows 的 WebView2），不是 Google Chrome 浏览器。Windows 11 已预装 WebView2；旧版 Windows 的安装包可以附带 WebView2 安装器。

**误解 2：系统 WebView 意味着所有平台表现完全一样。**
纠正：不同平台使用不同的 WebView 引擎。Windows 用 WebView2 (Chromium)，macOS 用 WKWebView (WebKit)，Linux 用 WebKitGTK。虽然都支持 Web 标准，但在 CSS 渲染、JS API 支持、性能特征上可能有细微差异。跨平台测试是必要的。

**误解 3：Tauri 前端可以直接使用 Node.js 模块。**
纠正：Tauri 前端运行在 WebView 中，不是 Node.js 环境。`require('fs')`、`require('child_process')` 等都不能用。需要系统能力时，必须通过 Tauri 插件或自定义 Rust 命令。

**误解 4：轻量打包意味着功能受限。**
纠正：Tauri 通过 Rust 命令和插件系统提供了丰富的系统能力：文件操作、对话框、窗口管理、菜单、托盘、Shell 执行、自动更新等。"轻量"来自架构选择（复用系统 WebView），不是功能裁剪。

## Socratic Check

**检验问题 1：**
如果你的 Tauri 应用需要在 Windows 10 旧版本上运行，而该版本没有预装 WebView2，会发生什么？你应该怎么处理？

答案：应用可能无法正常启动，因为缺少 WebView2 Runtime。处理方式是在安装包中附带 WebView2 引导安装程序（bootstrap），或者在应用启动时检测并提示用户安装。Tauri 的打包工具（如 tauri-bundler）可以配置自动包含 WebView2 安装逻辑。

**检验问题 2：**
为什么 Tauri 的前端不能直接 `fetch('file:///C:/data.json')` 来读取本地文件？

答案：因为 WebView 中的前端运行在受限的安全沙箱中。`file://` 协议在 WebView 中通常被禁止或受限。Tauri 的设计哲学是：前端发请求，Rust 后端执行受控的系统操作，权限由 capabilities 和 permissions 配置决定。这是安全边界的体现。

## Quick Summary

- Tauri = Web UI + 系统 WebView + Rust 后端，轻量来自复用系统 WebView 而非捆绑 Chromium
- 系统 WebView 因平台而异（Windows: WebView2, macOS: WKWebView, Linux: WebKitGTK），跨平台测试必要
- 前端不是 Node 环境，系统能力必须通过 Rust 命令或 Tauri 插件访问
- 轻量 ≠ 功能弱，Tauri 通过 Rust 和插件系统提供丰富的系统能力
- 安全边界清晰：前端发请求 → Rust 执行 → 权限配置控制
