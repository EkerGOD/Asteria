## Positioning

**IPC 消息传递** 位于 Tauri 知识树的 **架构与运行模型** 分支，是「Rust 后端与前端边界」的自然延伸。你已经知道前端和 Rust 之间有一条边界，现在要深入理解：这条边界上的"通信协议"是什么？消息怎么发、怎么收、怎么保证类型安全？

在 Tauri 中，IPC（Inter-Process Communication，进程间通信）是连接前端和 Rust 后端的桥梁。没有 IPC，两层就是完全隔离的孤岛。

## Analogy

把 Tauri 的 IPC 想象成**外卖系统**。

前端（WebView）是**点餐的顾客**：顾客通过外卖 App（invoke）下单，说清楚要什么菜（命令名）和具体要求（参数）。

Rust 后端是**厨房**：厨师（命令处理函数）接到订单后做菜，做完后通过外卖系统把结果送回去。

IPC 系统就是**外卖平台**：
- 它负责把订单从顾客传到厨房（请求路由）
- 它负责把做好的菜从厨房送回顾客（响应返回）
- 它还要处理异常情况（菜做不了、地址错误等）

Tauri 提供两种 IPC 模式：
1. **命令（Command）**：顾客主动点餐，厨房做完送回 → 请求-响应模式
2. **事件（Event）**：厨房广播通知（"今日特价！"），所有顾客都能听到 → 发布-订阅模式

## Core Mechanism

### 一、两种 IPC 模式概览

```
┌─────────────────────────────────────────────────────┐
│                    Tauri IPC                         │
├──────────────────────┬──────────────────────────────┤
│    命令 (Command)     │      事件 (Event)             │
│   请求-响应模式        │     发布-订阅模式              │
│                      │                              │
│  前端 invoke()       │  前端 emit() / Rust emit()   │
│       ↓              │       ↓                      │
│  Rust 命令函数        │  前端 listen() / Rust listen()│
│       ↓              │                              │
│  返回结果给前端       │  消息广播给所有监听者           │
├──────────────────────┴──────────────────────────────┤
│  特点：一对一、同步等待、有返回值                      │
│  特点：一对多、异步通知、无返回值（或单向）              │
└─────────────────────────────────────────────────────┘
```

### 二、命令（Command）：请求-响应模式

命令是最常用的 IPC 方式。前端发起请求，Rust 处理后返回结果。

**流程：**
```
前端 invoke("command_name", { args })
    ↓ (序列化参数为 JSON)
Tauri IPC 层
    ↓ (路由到对应的 Rust 函数)
Rust #[tauri::command] fn command_name(args) -> Result<T, E>
    ↓ (执行逻辑，返回结果)
Tauri IPC 层
    ↓ (序列化结果为 JSON)
前端接收 Promise<T> 或捕获错误
```

**关键特性：**
- 前端用 `invoke()` 发起，返回 Promise（异步）
- Rust 用 `#[tauri::command]` 标记函数
- 参数和返回值自动序列化/反序列化（默认 JSON，也可用 bincode）
- 支持复杂类型：结构体、枚举、Vec、Option 等
- 错误处理：Rust 返回 `Result<T, E>`，前端用 try/catch

### 三、事件（Event）：发布-订阅模式

事件用于不需要返回值的异步通知场景。

**流程：**
```
发送方 emit("event_name", payload)
    ↓
Tauri 事件系统
    ↓
所有监听方 listen("event_name", callback)
    ↓
callback 被触发，收到 payload
```

**事件的方向：**
- **前端 → Rust**：前端 `emit()`，Rust `listen()`
- **Rust → 前端**：Rust `emit()`，前端 `listen()`
- **前端 → 前端**：理论上可以，但通常不推荐（用前端框架的状态管理更好）

**关键特性：**
- 一对多：一个事件可以被多个监听器接收
- 异步通知：发送方不等待接收方处理完
- 无返回值：事件是"通知"，不是"请求"
- 支持 payload：可以携带数据

### 四、类型传递：序列化与反序列化

IPC 的核心挑战是：前端（JavaScript）和 Rust 是两种完全不同的类型系统，怎么传递数据？

**Tauri 的方案：serde（序列化框架）**

```
JavaScript 对象  ←→  JSON/bincode  ←→  Rust 结构体
```

**支持的类型映射：**

| JavaScript | Rust | 说明 |
|-----------|------|------|
| `string` | `String` / `&str` | 字符串 |
| `number` (整数) | `i32` / `u32` / `i64` 等 | 整数 |
| `number` (浮点) | `f64` | 浮点数 |
| `boolean` | `bool` | 布尔值 |
| `null` / `undefined` | `Option<T>` (None) | 可选值 |
| `Array` | `Vec<T>` | 数组 |
| `Object` | `struct` | 结构体 |
| 联合类型 | `enum` | 枚举 |

**结构体示例：**

```rust
// Rust 端定义
#[derive(serde::Serialize, serde::Deserialize)]
struct UserProfile {
    name: String,
    age: u32,
    email: Option<String>,  // 可选字段
    tags: Vec<String>,      // 数组
}
```

```typescript
// TypeScript 端对应（手动定义或使用 tauri-specta 自动生成）
interface UserProfile {
  name: string;
  age: number;
  email?: string;  // 可选
  tags: string[];
}
```

### 五、命令的高级用法

**1. 访问应用上下文（AppHandle）**

```rust
#[tauri::command]
async fn do_something(app: tauri::AppHandle) -> Result<(), String> {
    // AppHandle 可以访问应用的各种能力
    // 例如：emit 事件、获取窗口、访问状态等
    app.emit("progress", "Processing...").map_err(|e| e.to_string())?;
    Ok(())
}
```

**2. 访问共享状态（State）**

```rust
struct DatabasePool { /* ... */ }

#[tauri::command]
fn query_data(state: tauri::State<DatabasePool>) -> Vec<String> {
    // 使用共享的数据库连接池
    vec!["result1".to_string(), "result2".to_string()]
}
```

**3. 异步命令**

```rust
#[tauri::command]
async fn fetch_remote_data(url: String) -> Result<String, String> {
    // 异步命令不会阻塞 Tauri 的事件循环
    let response = reqwest::get(&url).await
        .map_err(|e| e.to_string())?;
    response.text().await.map_err(|e| e.to_string())
}
```

**4. 访问窗口（Window）**

```rust
#[tauri::command]
fn update_window_title(window: tauri::Window, title: String) {
    window.set_title(&title).ok();
}
```

### 六、IPC 性能考量

| 因素 | 建议 |
|------|------|
| 序列化开销 | 小数据用 JSON（默认），大数据考虑 bincode |
| 频繁调用 | 合并请求，避免大量小 IPC 往返 |
| 大文件传输 | 用文件路径代替文件内容，Rust 端直接读文件 |
| 实时性要求高 | 考虑事件流（Event Stream）或通道（Channel） |

## Code Example

```rust
// src-tauri/src/lib.rs

use tauri::{Emitter, State};
use serde::{Serialize, Deserialize};

// ===== 类型定义 =====

#[derive(Serialize, Deserialize, Clone)]
struct Task {
    id: u32,
    title: String,
    completed: bool,
}

#[derive(Serialize, Deserialize)]
struct CreateTaskRequest {
    title: String,
}

// ===== 共享状态 =====

struct TaskStore {
    tasks: std::sync::Mutex<Vec<Task>>,
}

// ===== 命令（Command）=====

// 命令 1：获取所有任务
#[tauri::command]
fn get_tasks(store: State<TaskStore>) -> Vec<Task> {
    store.tasks.lock().unwrap().clone()
}

// 命令 2：创建任务
#[tauri::command]
fn create_task(
    req: CreateTaskRequest,
    store: State<TaskStore>,
    app: tauri::AppHandle,
) -> Result<Task, String> {
    let mut tasks = store.tasks.lock().unwrap();
    let new_task = Task {
        id: tasks.len() as u32 + 1,
        title: req.title,
        completed: false,
    };
    tasks.push(new_task.clone());

    // 创建成功后，向所有前端窗口广播事件
    app.emit("task-created", &new_task).map_err(|e| e.to_string())?;

    Ok(new_task)
}

// 命令 3：切换任务完成状态
#[tauri::command]
fn toggle_task(id: u32, store: State<TaskStore>) -> Result<Task, String> {
    let mut tasks = store.tasks.lock().unwrap();
    if let Some(task) = tasks.iter_mut().find(|t| t.id == id) {
        task.completed = !task.completed;
        Ok(task.clone())
    } else {
        Err(format!("Task {} not found", id))
    }
}

// 命令 4：异步命令（不阻塞事件循环）
#[tauri::command]
async fn export_tasks(store: State<'_, TaskStore>) -> Result<String, String> {
    let tasks = store.tasks.lock().unwrap().clone();
    // 模拟耗时操作
    tokio::time::sleep(tokio::time::Duration::from_secs(1)).await;
    serde_json::to_string(&tasks).map_err(|e| e.to_string())
}

// ===== 应用构建 =====

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .manage(TaskStore {
            tasks: std::sync::Mutex::new(vec![]),
        })
        .invoke_handler(tauri::generate_handler![
            get_tasks,
            create_task,
            toggle_task,
            export_tasks,
        ])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

```typescript
// 前端：使用 IPC 与 Rust 后端通信

import { listen, emit } from "@tauri-apps/api/event";

// ===== 类型定义（与 Rust 端对应）=====

interface Task {
  id: number;
  title: string;
  completed: boolean;
}

interface CreateTaskRequest {
  title: string;
}

// ===== 命令调用 =====

// 获取所有任务
async function loadTasks(): Promise<Task[]> {
  return await invoke<Task[]>("get_tasks");
}

// 创建任务

  const req: CreateTaskRequest = { title };
  return await invoke<Task>("create_task", { req });
}

// 切换任务状态
async function toggleTask(id: number): Promise<Task> {
  return await invoke<Task>("toggle_task", { id });
}

// 异步导出任务
async function exportTasks(): Promise<string> {
  return await invoke<string>("export_tasks");
}

// ===== 事件监听 =====

// 监听任务创建事件（Rust 端发出的）
async function setupEventListeners() {
  // 监听 task-created 事件
  await listen<Task>("task-created", (event) => {
    console.log("New task created:", event.payload);
    // 更新 UI...
  });

  // 前端也可以发事件给 Rust
  await emit("user-action", { action: "opened_app" });
}

      const newTask = await addTask(title);
      appendTask(newTask);
    }
  });
}

}

function appendTask(task: Task) {

}

main();
```

这段代码完整展示了 Tauri IPC 的两种模式：

**命令模式（invoke）：**
- `get_tasks`、`create_task`、`toggle_task`、`export_tasks` 都是命令
- 前端用 `invoke()` 调用，等待 Promise 返回
- Rust 端用 `#[tauri::command]` 定义，可以访问 State、AppHandle 等

**事件模式（emit/listen）：**
- `create_task` 命令执行后，通过 `app.emit("task-created", ...)` 广播事件
- 前端用 `listen()` 监听事件，收到通知后更新 UI
- 事件是单向通知，不需要返回值

## Common Misconceptions

**误解 1：invoke 是同步调用，会阻塞前端。**
纠正：`invoke()` 返回 Promise，是异步的。它不会阻塞 WebView 的主线程。Rust 命令在 Tauri 的线程池中执行，执行完后通过 IPC 把结果返回给前端。如果 Rust 命令耗时较长，前端可以用 `await` 等待，同时 UI 保持响应。

**误解 2：命令参数和返回值只能是简单类型（string、number）。**
纠正：Tauri 通过 serde 支持复杂的类型映射。结构体、枚举、Vec、Option、嵌套对象都可以传递。只要 Rust 端的类型实现了 `Serialize` 和 `Deserialize` trait，前端有对应的 TypeScript 类型定义，就可以自动序列化/反序列化。

**误解 3：事件和命令可以互相替代。**
纠正：它们解决不同的问题。命令适合"请求-响应"场景（前端需要 Rust 的处理结果）；事件适合"通知"场景（Rust 需要告诉前端某事发生了，但不需要返回值）。例如：获取文件内容用命令；文件变化通知用事件。

**误解 4：IPC 通信很慢，应该避免频繁调用。**
纠正：IPC 有序列化开销，但本地 IPC 通常很快（微秒级）。对于正常的应用交互（点击按钮、加载数据），性能不是问题。需要注意的是：避免在循环中发送大量小消息（考虑批量处理），避免传输大文件内容（用文件路径代替）。

**误解 5：前端和 Rust 可以直接共享 JavaScript 对象或 Rust 引用。**
纠正：IPC 是"消息传递"，不是"共享内存"。每次调用都会序列化数据、传输、反序列化。前端拿到的是 Rust 数据的"副本"，不是引用。修改前端的对象不会影响 Rust 端的状态，反之亦然。

## Socratic Check

**检验问题 1：**
假设你要实现一个"进度条"功能：Rust 后端在处理一个耗时任务，需要实时把进度（0-100%）通知给前端更新 UI。应该用命令还是事件？为什么？

答案：应该用事件。因为这是"Rust 主动通知前端"的场景，不需要前端请求。Rust 在处理过程中多次 `emit("progress", percentage)`，前端 `listen("progress", callback)` 接收并更新 UI。如果用命令，前端需要不断轮询，效率低且实时性差。

**检验问题 2：**
如果你在 Rust 命令中返回一个包含 100 万条记录的 Vec，会有什么性能问题？怎么优化？

答案：主要问题是序列化/反序列化开销和内存占用。100 万条记录序列化为 JSON 会很大，传输和解析都慢。优化方案：(1) 分页返回，每次只返回一部分；(2) 用 bincode 代替 JSON（更紧凑）；(3) 如果数据来自文件，让前端传文件路径，Rust 直接处理文件而不是把内容全传回去。

## Quick Summary

- Tauri IPC 有两种模式：命令（请求-响应）和事件（发布-订阅）
- 命令用 `invoke()` + `#[tauri::command]`，适合需要返回值的操作
- 事件用 `emit()` + `listen()`，适合异步通知和广播
- 类型通过 serde 自动序列化/反序列化，支持结构体、枚举等复杂类型
- 命令可以访问 AppHandle、State、Window 等上下文
- 性能注意：避免大量小消息、大文件传输用路径代替内容
